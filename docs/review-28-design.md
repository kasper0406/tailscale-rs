## Findings by severity

### High — wrong default artifact and no recovery transaction

`runner/env.sh:3` and `deploy/launchd/update.sh:8` still select `repos/geiserx-tailscale-rs`, whose HEAD is `ts-exit/main` `fcb6dbe`, not the candidate worktree. Consequently, the documented build/update sequence can install the old binary with the new wrapper. That binary lacks `--serve-tcp`: it exits on argument parsing and KeepAlive repeatedly restarts it. `update.sh:11–16` overwrites the only binary, replaces scripts nonatomically, kills the node and checks only process existence. An incompatible binary, partial wrapper, registration failure or dead listener has no automatic rollback. Updating through `ssh kmini` will also terminate that management session.

**Fix before switching:** build from `scratch/wt-gx` at the verified SHA using the locked exitnode/ring configuration; pass its binary explicitly to the updater. Stage binary, wrapper and rotator together on the internal disk, retain the complete previous release, then atomically select a release directory. Arm a local rollback timer before stopping the old process; cancel it only after external SSH, DNS and exit-traffic probes succeed. Keep an existing independent SSH/management route available. Do not start two nodes against the same identity, or copy identity secrets into release directories. A PID after 15 seconds is insufficient readiness evidence.

### High — logging can stall service; wrapper errors have no disk bound

`run.sh:22` puts a synchronous pipe between tracing and the rotator. If Perl or disk I/O hangs, the pipe fills; logging can block runtime workers. KeepAlive detects an exited wrapper, not this condition. If Perl exits, the node can instead continue with failed/lost log writes; do not assume SIGPIPE restarts Rust. `rotate.pl:20–27` ignores print, close and rename failures, and line-based input has no maximum record size. Five archives plus the active file nominally use ~60 MiB, but that is not a strict bound. `dev.kasper.rust-exit.plist:48–51` directs wrapper/Perl errors into an entirely unrotated `launchd.log`.

**Fix:** check every rotation operation and bound both logs, including oversized records. Decouple network progress from log writes with a bounded, nonblocking logger and an explicit drop policy/health signal; supervise logger failure. Alert on internal-disk free space and stale health probes. Until hardened, retain an independent management path and keep logging volume low. Launchd supervision alone does not make this pipeline reliable.

### Medium — Serve can silently fail while the node stays healthy

`Device::set_serve_config` returns after scheduling listeners (`G/src/lib.rs:1953`; `G/ts_runtime/src/serve.rs:170`). Binding happens later (`serve.rs:234`); failure only emits a warning and exits that task. A duplicate/conflicting port can therefore leave the exit node running and the example logging “forwarding,” with no SSH listener and no launchd restart.

**Fix for the serve PR:** bind successfully before acknowledging configuration, propagate bind failures, and expose listener health. Reject duplicate ports and collisions with peerAPI/sink ports. For this deployment, require a fresh external SSH connection after each restart; configuration success is not readiness.

### Medium — loopback loses the original SSH source identity

`G/ts_runtime/src/serve.rs:371–378` opens an ordinary local TCP connection. Every tailnet caller looks like `127.0.0.1` to sshd. This can defeat address-based distinctions or make one caller's authentication failures penalize all callers. **Fix:** restrict tailnet TCP/22 to Kasper's intended devices/identity and examine effective sshd settings for loopback-specific trust, `Match Address`, `AllowUsers user@host`, authorized-key `from=` restrictions and per-source penalties. Preserve independent SSH access; do not disable authentication or rate limits globally to make the proxy work. The actual policy was not supplied, so “only laptop/iPad” remains a deployment check, not an established fact.

### Medium — FileVault remains a recovery dependency

`RUNBOOK.md:170–171` treats `fdesetup authrestart` as a universal remedy. The local `fdesetup(8)` manual explicitly makes it hardware-dependent (`/usr/share/man/man8/fdesetup.8:234,263`); even a positive support check is not a reboot test. Power loss or an ordinary reboot can strand the node behind FileVault. **Fix:** no reboot during this switch. Establish support and a separately reachable unlock/recovery path before scheduling future restarts. Apple now supports SSH FileVault unlock on Apple silicon with macOS 26+, but this Rust daemon cannot carry that SSH connection while its encrypted files are unavailable. [Apple FileVault documentation](https://support.apple.com/en-ca/guide/security/sec8447f5049/web).

### Low — operating instructions contradict the proposed deployment

`RUNBOOK.md:160` still specifies 1 MiB; `:172` still names `rust-exit`. More seriously, `RUNBOOK.md:28–36` and `docs/DECISIONS.md:15` prescribe storing an enrollment auth key, violating the stated no-auth-key-files constraint. **Fix in a later documentation change:** record the exact release/controller/window, correct the name and onboarding instructions, and distinguish enrollment auth keys from the required persisted machine/node private keys. The draft daemon passes no auth-key file (`run.sh:20`); preserve the existing identity and never print its contents.

**256 KiB is the prudent starting value, not the throughput optimum.** At 25 ms its ideal single-flow ceiling is ~84 Mbit/s; at the ~29 ms effective RTT in F31, ~72 Mbit/s. BDP across 50–250 Mbit/s is ~153–763 KiB. Thus it can fill a 50 Mbit/s link but cannot fill 150–250 Mbit/s with one flow. Parallel flows can exceed that single-flow cap. Allocation is eager: ~512 KiB/socket at default, versus ~2 MiB/socket at 1 MiB (`G/ts_netstack_smoltcp_core/src/config.rs:102`).

F31's large-window failures were on a different controller/recovery build; F34/F35's 1 MiB success used the patched sender (`docs/DECISIONS.md:237–249,288–309`; `docs/TCP-RECOVERY-24.md:94`). Neither predicts exact stock-Reno performance. Stock 0.14 already has flight-size cwnd accounting, Reno ACK/RTO corrections and zero-window probes, plus the fast-retransmit/RTO separation that supersedes our backport. It still lacks sender SACK/NewReno and retains a one-second RTO floor. I checked the cached and freshly downloaded published archive against the lockfile checksum and inspected `tcp.rs:1397,2091,2480`, `congestion/reno.rs:40–99`; do not attribute every 0.13 defect to 0.14. [Published source](https://docs.rs/smoltcp/0.14.0/src/smoltcp/socket/tcp.rs.html).

Keep 256 KiB initially; compare 512 KiB/1 MiB only after checking lossy single/parallel downloads, uploads and loaded latency on the actual stock build. Reverting to 256 KiB accepts a likely single-download regression from F35's ~20 MB/s in exchange for a conservative rollout.

## 3. Serve security and behaviour

Incoming WireGuard traffic first undergoes peer-source validation and the live userspace packet filter (`G/ts_dataplane/src/lib.rs:1754–1785`, identical to our tree). Serve has no separate bypass: allowed traffic then reaches the application netstack. Network ACL/grant permission to this node's TCP/22 is required; exit-node permission through `autogroup:internet` alone does not grant node SSH. A broad allow-all policy permits every matching peer. This is native macOS SSH carried over WireGuard, not Tailscale SSH: its `ssh` policy/check-mode rules do not authenticate this connection. [Serve access-control behaviour](https://tailscale.com/docs/features/tailscale-serve).

The node's own host route wins over `/0` and targets the application stack; the exit forwarder cannot steal its TCP/22 (`G/ts_runtime/src/route_updater.rs:415–438`). That assertion concerns the node's **tailnet** IP; internet destinations still use the exit path. Serve binds only the overlay IPv4 (`serve.rs:232–234`), so no privileged host port bind/root/TUN is needed. An IPv6 backend does not imply an IPv6 tailnet listener. Use the actual MagicDNS A record/full tailnet name when diagnosing `ssh kmini`.

The loopback connection preserves SSH encryption, host-key checks and normal sshd authentication. The observed macOS configuration enables PAM (`/etc/ssh/sshd_config.d/100-macos.conf:2`), with account checks including SSH Remote Login SACL and OpenDirectory (`/etc/pam.d/sshd:6–8`); forwarding does not remove those username/account checks. Source-based rules change meaning: `AllowUsers kasper` still restricts the user, while `kasper@<laptop-address>` cannot match. A permissive localhost `Match` can weaken authentication; authorized-key `from=` restrictions can instead reject legitimate users. Per-source penalties see one common address, and SSH logs lose per-device attribution (`/usr/share/man/man5/sshd_config.5:164–175,1588–1619`). No such custom rules were observed in the inspected sshd config, but effective per-user/key restrictions were not audited.

If sshd is down, Serve accepts the overlay TCP connection, the loopback dial fails, and that connection is dropped; the listener/node remain running and later connections can succeed when sshd returns (`serve.rs:370–379`). Expect connect-then-close, not necessarily an initial SYN refusal. No fallback dial occurs.

Literal `SocketAddr` plus loopback checking prevents hostname/DNS rebinding and arbitrary LAN targets (`G/examples/exit_node/main.rs:105–120`), but cannot make every localhost service safe to expose. It permits backend port zero and repeated front ports currently overwrite earlier entries (`:216–223`). Validate backend port, collisions and intended service; retain SSH auth. Serve caps active handlers at 256/port, with additional bounded listener backlog, not 256 total sockets (`serve.rs:59,238`; netstack config `:106`).

## 4. Launchd and remote availability

The plist is structurally valid. System-domain `UserName` applies before user login, once FileVault has unlocked; the root-owned plist does not make the node root (`dev.kasper.rust-exit.plist:9–24`; `launchd.plist(5):135`). Explicit HOME and WorkingDirectory point inside the internal home directory. Decimal umask 63 is octal 077. Interactive avoids background throttling and is reasonable for latency-sensitive forwarding; KeepAlive/10-second throttle restarts exits, including successful exits, but cannot diagnose a wedged node. The 61,440 soft/hard FD settings are plausible; verify the actual child's effective limit rather than assuming the requested value was granted. `GroupName=staff` fits this account; supplementary groups remain initialized by default. No host route, resolver, PF or TUN changes are introduced by this invocation (`G/examples/exit_node/main.rs:160–180`; default Netstack transport in `G/src/config.rs:743`).

The zsh wrapper's `$!` identifies the node, traps forward TERM/INT/HUP, and repeated waits handle interrupted `wait` (`run.sh:23–28`). Zsh's normal scalar expansion handles the space-containing app path. It intentionally supervises a child rather than using `exec`; launchd's default process-group cleanup covers leftover children (`launchd.plist(5):609`). The rotator is not explicitly supervised or drained; shutdown/crash can lose queued final log records. Specify a finite shutdown deadline if deterministic cleanup is required. Do not infer “healthy node” from the wrapper PID.

The installed runtime paths avoid `/Volumes/git`: USB absence before login affects future builds/updates, not daemon startup (`install.sh:9–22`, plist `:16,24`). Confirm these paths are real internal files, not symlinks back to USB. Observed read-only power settings are `sleep=0`, `disksleep=0`, `autorestart=1`; display sleep is harmless. Network wake is not a substitute for keeping the Mac awake. Auto-restart after power loss still encounters FileVault. The observed OS is 26.6.2; Apple's new remote unlock support is relevant, but no independent pre-unlock reachability was established.

Install migration uses owner-only identity files and stops a PID-recorded manual instance (`install.sh:24–39`), but trusts a potentially stale PID and does not prove exclusive identity use. Reinstallation overwrites scripts before bootout; use the transactional release approach above. `uninstall.sh:5–7` ignores bootout failure and then removes the plist, so it can report success while the node survives until the next reboot. Require successful stop, confirm node/rotator exit, then remove the plist. Retaining identity/logs is correct; never run uninstall via the sole management connection without a recovery route.

**Detect remotely:** use fresh TCP/22 SSH connections, an exit-node HTTPS fetch and DNS lookup from the laptop/iPad, plus client path/online status. Through independent management, check `launchctl print system/dev.kasper.rust-exit`, actual child UID/FD limit, recent status logs, listener warnings, logger process, disk space and node-key expiry. An alive PID with failed SSH suggests listener/backend trouble; SSH working but failed DNS/exit fetch suggests forwarding/resolver trouble. All probes failing after reboot cannot distinguish FileVault from power/network failure without independent access. External monitoring should alert on that condition; local KeepAlive is insufficient.

## 5. Naming

Renaming an existing identity changes its display/MagicDNS name, not machine identity, tags or route approvals. Clients already selecting the same stable node generally keep their choice; scripts selecting `rust-exit` by name need updating, and both laptop/iPad should confirm the selected exit after restart. The server requests `kmini` but control assigns the canonical name (`G/examples/exit_node/main.rs:163`). Another registered client on this Mac can create a collision and a suffix such as `kmini-1`; a local SSH alias or other DNS search domain can also send bare `kmini` elsewhere. Verify the actual name/address and SSH host key without bypassing host-key checks. [Machine naming rules](https://tailscale.com/docs/concepts/machine-names), [device identity](https://tailscale.com/docs/concepts/tailscale-identity).

Retain `tag:rust-exit` for policy independent of the display name. Tagged nodes normally have expiry disabled on initial tagged authentication, but verify this node's current console setting; renaming does not extend expiry. Enrollment-key expiry is separate from node-key expiry. Missing state plus `--interactive` can create a newly owned, untagged identity requiring login and route approval rather than restoring the old one (`run.sh:16`; example `:41–45,143–150`). Keep the existing 0600 state protected and backed up privately. [Tagged key-expiry behaviour](https://tailscale.com/docs/features/tags).

## 6. Forward path

Upstream-first is the right direction. Rebase the smoltcp work against current upstream and subtract fixes already present in 0.14; do not mechanically submit the old vendor diff. Offer small independently tested changes: NewReno partial-ACK recovery, bounded sender SACK, then optional pacing/configurable RTO policy. Preserve wraparound/SACK validation from F34's security fix, deterministic multi-loss/reordering/tail-loss tests, no_std and 32-bit checks. Propose the serve flag to GeiserX together with bind/readiness handling and end-to-end allow/deny/routing/backend-failure tests. Keep deployment scripts and benchmark tooling locally; retiring the layered product fork does not retire this Mac's operational glue.

A temporary `[patch.crates-io]` is viable **after porting** to a version satisfying `0.14` and reviewing the lockfile. Point to a pinned, reproducible patched 0.14 source; the old version-0.13.1 vendor cannot replace it. The Cargo override alone also does not activate optional pacing/200 ms floor: restore their netstack integration explicitly, and note that GeiserX now pins Reno regardless of a Cubic feature. Carry that integration as a small auditable delta; do not lose upstream security/availability fixes just to retain the old vendor.

For 50 Mbit/s, stock Reno/256 KiB is likely sufficient. At 150–250 Mbit/s/25 ms, larger windows plus recovery have a demonstrated practical value: F35 roughly doubled single-flow rates, and F34 eliminated long lossy-path pauses. A temporary patch is worth carrying if the exact stock build shows those user-visible problems again; benchmark before accepting its maintenance cost. Prefer testing GeiserX + patched 0.14 over continuing the aging full fork. Keep the known-working old release available during that decision.

Validation: plist lint and Perl syntax passed; zsh no-execute parsing returned success (the sandbox emitted a background `nice` diagnostic). Source/commit comparisons and archive checksum verification are complete. Live readiness, ACL denial, rollback and reboot recovery remain untested by design.
