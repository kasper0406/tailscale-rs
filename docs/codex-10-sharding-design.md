# Flow sharding: independent design review

2026-10-12. Evidence: worktree base `ae21eff` on `ts-exit/perf-connected` (`4168f38`), current runner source read only, `BENCHMARKS.md` §1c, `pipeline-controlled.txt`, and `scratch/prof/pipeline-single-8.txt`. Line references below use the worktree base unless described as current runner. No sharding implementation is proposed for merge in this delivery.

**Agree with sticky flow ownership, including host sockets and per-flow tasks. Disagree that the sketch is already a complete scalable architecture.** Replace the fixed stage split with flow shards, but explicitly retain a peer/session control owner and platform-dependent socket owners. “Thread per core” is placement intent, not guaranteed macOS CPU affinity. A configurable number of sticky threads is the supported contract.

The controlled same-binary A/B establishes substantial CPU savings from isolation, and an aggregate-throughput regression. The new eight-flow profile has send syscalls ~40%, crypto ~16%, netstack ~10%, allocation/copy ~11%, and scheduler/locks/clock ~2% each. This supports investigating batch formation and syscall capacity before assuming netstack is the limiting stage. Sample percentages are stack occupancy, not calibrated CPU costs. A stage split can help diagnose the bottleneck but retains a fixed serial ceiling; park it. Neither that profile nor the 86%-of-core observation predicts linear sharding gains. D15's “3.6 bounds the gain” remains unsupported; N=1 with colocated splices is a new variant, not today's single packet thread.

## Conditions that must be settled

1. **One TCP owner for both directions, selected once.** Hash a canonical bidirectional tuple, namespace it by authenticated peer/source identity, and keep the assignment stable through FIN/RST, pending commands and TIME_WAIT. SYN retransmissions must find the same owner. Resize affects new flows only; migrating live smoltcp sockets is outside the first implementation. Peer namespacing in the hash alone does not namespace smoltcp socket tuples: require unique authorized source ownership within a stack (or distinct routing domains), and retire old flows on address reassignment. Use a keyed hash so a peer cannot cheaply choose all tuples for one shard. Bound each shard's queue and flow count; expose drops and occupancy. Unlimited queues conceal overload as latency and memory.

2. **The per-port gate belongs to the stack, not the whole node.** any-IP does not make a listener on shard A match shard B. Each shard needs its own listener registration, generation and gate; keep the gate before smoltcp, including the first SYN. Current gate has two 65,536-slot vectors (`ts_forwarder/src/port_gate.rs:63,124`), a 1 MiB held-packet budget (`:48`) and listener generations (`:204`). Replication is simplest but costs memory: the current 12-byte slots alone cost ~1.5 MiB per gate (~12 MiB at eight shards), plus held packets and maps. Existing all-port limits of 1,024 ports and 2,048 TCP/UDP flows (`all_port.rs:62,83,92`) are currently per forwarder: replicating them must not silently multiply the node's admission limits by N. Share the global admission semaphore and/or explicitly partition it, while maintaining local fairness. TCP buffers are two times `tcp_buffer_size` per socket, default 256 KiB each (`ts_netstack_smoltcp_core/src/config.rs:27,97`); listeners also allocate sockets (`socket_impl/tcp/listener.rs:89,334`). Count idle listeners, SYN backlog, established sockets and UDP flows, not just active splice buffers. For example, 2,048 established flows alone cost approximately 1 GiB at 256 KiB, 8 GiB at 2 MiB, before listener/backlog overhead.

3. **Fragment fallback in the proposal is incorrect.** A first fragment with ports hashes by five-tuple; its later fragments hash by three-tuple and can enter another stack's reassembler. Initially steer *all fragmented packets*, including first fragments, by authenticated peer + src/dst/protocol + fragment ID. This sacrifices flow distribution for fragmented traffic and needs a consistent reverse/reply routing rule. Alternatively use bounded reassembly before five-tuple dispatch, with explicit overlap/timeout/byte limits; this creates a serial reassembly resource but can be rare. A first-fragment association cache must handle later-fragment-first arrival and bound hostile IDs. Do not make an unbounded global fragment cache. Keep the dataplane's existing fragment/ACL restrictions (`ts_dataplane/src/lib.rs:453`) before stack delivery.

4. **WireGuard keys are not simply shared read-only state.** The current transmit API already takes `&self` and reserves nonce ranges under a short mutex (`ts_tunnel/src/session.rs:106,113,230`); an atomic is an optimization, not a prerequisite. Share the *same transmit-session object*, never instantiate multiple counters with the same key/receiver ID. Exhaustion, rekey, expiry and static-key replacement remain mandatory. Publish session references with generations; stop using expired/removed generations at both RX admission and TX, including queued batches. A retained Arc must not authorize sending forever. Endpoint owns handshake/session promotion/timers (`endpoint.rs:1099,1187`), so parallel transport-data views need a deliberate API and one owner for those transitions.

   RX may authenticate outside the replay lock, but **authenticated check-and-mark must be atomic under that lock** before releasing plaintext. Two concurrent packets with one nonce must yield one delivery. Never advance the window for a failed AEAD open. Old/current/next session lookup and expiry must be consistent. The receive API is presently `&mut self` (`session.rs:318`); replacing it with an Arc<Mutex<Endpoint>> would serialize the whole hot path. Current replay tolerance is 8,128 packets (`replay.rs:132`, also current runner), not arbitrary reordering. WireGuard permits reordered counters; it does not require every packet from a peer to be processed in wire order. However, reserving large nonce blocks then delaying a sender can evict valid lower counters at the remote end. Reserve at actual batch send, bound outstanding batches/reordering, and test parallel send/rekey/replay races. Preserve per-flow enqueue order where practical; more TCP reordering can erase the CPU gain.

5. **Receive ownership cannot be inferred from inner flows.** macOS connected socket demultiplexing sees one outer peer endpoint; SO_REUSEPORT cannot hash encrypted inner five-tuples. `bench/reuseport-check/src/main.rs:1,34` checks wildcard-versus-connected specificity, not parallel same-peer RX distribution, creation-order permutations, Linux behavior, or linear scalability. Raw synthetic peers also need disco/source binding: naked WG is dropped at `ts_magicsock/src/sock.rs:1557` when its UDP source is unknown, even with an admitted static key. The load tool therefore performs authenticated disco preflight on that same socket. Existing connected pumps are spawned at `ts_magicsock/src/connected.rs:300`; assigning each socket to one shard avoids dedicated RX threads and makes the first authenticated dispatch zero or one batch hop. It leaves a single heavy peer's RX socket/crypto owner as a possible bottleneck. Parallel decrypt workers help only after socket draining and add dispatch/replay contention. Measure one peer with many flows separately from many peers. Do not promise spreading one peer's connected socket across cores on macOS. Linux reuseport/BPF/offload needs a separate capability implementation and experiments, not copied Apple assumptions.

   Egress may send through a shared UDP fd from multiple runtimes, but a Tokio socket's registration and readiness wakers still belong to its originating reactor. Arc sharing does not create N reactor registrations. Either give each shard an independently registered send-only socket/duplicated fd with validated source-port behavior, or preserve a bounded batched socket-owner queue. Duplicating a fd retains the same kernel socket/locks; creating another connected socket with the same tuple can capture RX, so “send-only” requires explicit validation/pumps. Measure kernel socket lock/readiness contention and batch collapse. Avoid acquiring a per-peer send mutex across await. Current connected batching path is `sock.rs:1435`; the new offered-batch histogram will reveal whether eight flows actually reach sendmsg_x as useful batches.

6. **App services and non-TCP/UDP packets require their own dispatch contract.** Start with the app stack on shard 0; the public listen/dial APIs, peerapi, DNS and tunnel benchmark sink need one coherent address/port namespace. This deliberately leaves app/tunnel-only workloads on shard 0 and therefore cannot demonstrate exit-flow sharding. Sharding app listeners later needs an accept/dial facade and ephemeral-port ownership, not simply N copies of the same IP. Handle ICMP errors by the *quoted inner tuple* and deliver to the originating socket owner; handle echo by an explicit service owner. TSMP/disco-key advertisements and rejected-connection control messages are peer/node events (`ts_dataplane/src/async_tokio.rs:260,294`), not ordinary flow shards. DERP arrives through one relay connection, with its own framing and control tasks: authenticate and apply identical dispatch/security rules after that handoff. Keep IPv6 explicit rejection before any shard gate/dial (`ts_runtime/src/forwarder_actor.rs:307`). Host destination/LAN/loopback boundaries and source ownership must apply identically for every shard and every underlay.

7. **Security snapshots are a separate correctness change.** Current ordered bus + startup barrier + death supervision should remain until a snapshot API has its own review. Atomically swapping filters, source ownership, routes and peer generations separately is not a coherent snapshot. Define a security epoch and either publish one complete snapshot or specify safe transitions; packets queued before revocation must revalidate on dequeue/TX, and already-open relays need an explicit revocation policy. A map update cannot merely spawn N fire-and-forget subscriber messages. One independent supervisor can stop all shard admission and abort all pumps without asking a saturated mailbox (`ts_runtime/src/security.rs:22,96`). Aborts are cooperative: bounded drains are necessary, and synchronous capture callbacks/locks can still prevent task cancellation. Actor death supervision is not detection of an actor that is alive but stuck, or of every detached child/poll future that panics while its parent actor survives; shard/task exit must itself become a supervised failure signal. Require bounded inline hooks and document this limitation. DNS belongs on the caller; packet sockets remain on their owning runtime. Join/drop must not wait on stalled DNS in a shard's blocking pool.

## Staged plan: opt-in, independently shippable

| Stage | Delivery and invariant | Measurements / acceptance |
|---|---|---|
| 0 — this salvage | One packet thread remains; budgets, receive bridge coalescing, independent death supervisor, caller DNS, cheap counters, corrected harness and independent load peer. Two-stage topology parked. | Off/1 correctness/security suites; finite loss transfers; timer/flood/shutdown tests. Compare CPU/GB, bytes/flow, PPS, batch sizes and drops; no claimed live gain. |
| 1 — exit-flow ownership | N forwarder stacks + colocated listener/splice/UDP tasks. Stable authenticated flow dispatch; app stack and WG endpoint initially retain one owner. Node-wide limits and IPv6 policy unchanged. | N=1 versus previous 1 tests effect of moving splices; N=1/2/4/8 measures forwarder scaling only. Include reversed tuples, cold ports, ICMP quotes, fragments, teardown/revocation and one overloaded shard. Explicitly acknowledge retained WG/RX ceiling. |
| 2 — distributed transport data | Session-owner publishes generation-bound crypto views; per-batch nonce reservation, authenticated replay commit, expiry/rekey tests; each flow shard seals its own egress. Keep batched socket-owner handoff until multi-reactor send is validated. | Same-peer concurrent TX/RX + key change and removal, remote replay window pressure, failed authentication, DERP/direct transitions. Profile remaining owner/lock cost. |
| 3 — underlay ownership | Assign peer RX/connected pumps and send sockets to shards where supported; steer authenticated batches once; capability fallback elsewhere. Optimize receive/decrypt of one heavy peer only if it is the measured ceiling. | One peer × M flows and P peers × M flows; direct/DERP, Apple/Linux; count all cross-thread batches. Mixed small/bulk traffic and adversarial shard collision. |
| 4 — optional app scaling | Sharded app accept/dial namespace and service-specific dispatch, only if app benchmark/service workload needs it. | App sink and exit-to-host results reported separately; app shard 0 ceiling never presented as failed exit scaling. |

At every stage off remains the established behavior, and a failed shard stops forwarding globally. Reserve a distinct shard-count setting rather than reinterpret existing `TS_EXPERIMENT_PIPELINE_THREAD=1` silently. Do not expose “N=2” until it means flow sharding; the parked stage split is not that implementation.

The previous default bar (≥30% single-flow CPU saving, ≤5% aggregate loss, no >200 ms echo stalls in 8/8 runs) is a useful production gate on a controlled LAN, not a general scaling definition. The baseline itself stalls, and eight successes do not establish absence of rare stalls. Add confidence intervals, fixed offered load below/near/above saturation, bounded queue occupancy, per-flow fairness, PPS and memory versus N. Use remote load where possible, record generator CPU and verify it has headroom. A single flow remains serial, but its crypto/RX cost can be parallel; aggregate gains and CPU efficiency need not peak at the same N. On this M4, P/E-core placement and thermal state remain confounders. No sharding default should be chosen from the home line's ceiling.
